# Aether deep review

Find every defect this pull request introduces or exposes, and publish each one once with a concrete trigger. A missed real defect costs far more than an extra comment, so this review is built for recall: every agent starts from the same context pack, which shows each change inside its function with its callers, definitions and literals; every changed line, and every unchanged line printed beside it, is audited statement by statement by an auditor who first lists how each hunk could be wrong; every changed file is read from top to bottom by an owner who checks that the change agrees with the rest of the file; six independent reviewers read the whole diff; the results are merged and published without a confidence cutoff.

## 1. Scope

Review the pull request's changes from its merge base to its head, reading whatever repository context is needed to reason about them.

In scope: defects in or adjacent to the changed code. Wrong behavior, security and authorization gaps, races and non-atomic updates, data loss or corruption, broken API and type contracts, material performance regressions, newly required behavior with no test, and comments, docs or error messages the change made untrue. Every severity counts, including low: dead code, a misleading name or message, a missing cleanup. A statement that is correct only under an assumption the repository does not establish is in scope as a latent defect, and so is a behavior at a boundary value that differs from the ordinary case when nothing shows the difference is intended.

Out of scope: style, naming and refactoring preferences; speculation without a concrete trigger; pre-existing problems the change does not touch; anything about the environment the review ran in.

## 2. Context pack, brief, leads, audit, file owners and independent review

**Context pack.** Before anything else, build the pack. Fetch `https://raw.githubusercontent.com/aether-bench/review-tools/3c40455ad696f4384ad8d9da937baef5f53a3e76/context_pack.py` to `/tmp/review/context_pack.py`, write the pull request's title and description to `/tmp/review/pr_body.md`, and run `python3 /tmp/review/context_pack.py --base <merge base> --head HEAD --title "<title>" --body-file /tmp/review/pr_body.md --out /tmp/review/pack.md` from the repository root. The pack prints every hunk inside its enclosing function before and after the change, numbered per file as `git diff --unified=3` numbers them; each changed file's definition skeleton; the callers of every changed or removed function; the definitions of the functions the added lines call; and every literal the change adds or removes with its other occurrences in the repository, nearest first. It is generic tooling: it contains no bug rules and judges nothing. Every agent in this review reads the pack first and opens repository files only for what the pack does not show; the pack is a starting view, not a limit, and an agent that needs more than a dozen files beyond it says which and why in its result.

Write a brief: the changed files, each hunk in one line, and the contracts, callers, tests and schemas the change touches. Test files, fixtures, migrations, stylesheets and scripts are changed code too and get the same scrutiny as application code.

**Leads.** Run the stock analyzers that fit the changed files, with their default rule sets and no custom rules, limited to the departments that find defects rather than style: semgrep with the registry packs `p/default` and `p/security-audit`; ruff's default rule set and bandit for Python; rubocop restricted to its Lint, Security and ThreadSafety departments, with the rubocop-thread_safety extension, for Ruby; go vet for Go; the repository's own eslint configuration for JavaScript and TypeScript when its dependencies are already installed. Install what is missing with pip, gem or apt and skip an analyzer that does not install within a few minutes. Keep only the results that sit on a changed line or within three lines of one, and record each as a lead: file, line, tool, rule id, message. A lead is handed to the auditor who owns that line. It is published as a finding, at nit severity at least and naming the tool and rule, unless the auditor's row cites a line of the repository that makes the flagged condition impossible; "unlikely", "intended", "by convention" or a disagreement about severity is not a refutation.

Do not run review_triggers.py and do not invoke the installed aether-deep-review skill: the only scripted steps in this review are the context pack and the stock analyzers above, run with their default rule sets and no custom rules.

**Deal.** Take the diff from the merge base to the head with three lines of context (`git diff --unified=3 <merge base>...<head>`); its hunks are the pack's hunks. The audit covers every changed line and every context line git prints with it, because a change can break the unchanged line beside it. Let C be the number of changed lines. Run N auditors, N = C divided by 120 and rounded up, at least 2 and at most 12. Number the hunks in order and give hunk n to auditor (n mod N) + 1, so that every hunk is audited once and the auditors never see each other's work. An auditor's assignment is the list of its hunks with file, line ranges and hunk text, plus the leads on those lines.

**Auditors.** An auditor reads the pack, its hunks, the brief and whatever else it needs from the repository, and writes a ledger file. For each hunk it first writes a candidates list: at least three concrete ways the hunk could be wrong, each as the input, state or sequence that would show it, written before any statement is judged. Then it writes one row per statement in the hunk, changed or context: a line, or the smallest group of consecutive lines that forms one statement, declaration, call or expression. A row is keyed by file and the new-side line range it covers; a removed line is keyed by file and old-side line with a leading minus. Blank lines, delimiters and comment-only lines belong to the nearest statement's row and need no row of their own; a changed comment or docstring is a statement and gets a row that checks it is still true. Each row has this shape:

```
### <file>:<first line>-<last line>
S: <the statement, verbatim>
names: for every name, literal, key, field, route, option and constant on the statement: `<token>` defined at <file:line>; also used at <file:line, ...>; agrees: yes | NO, <the difference>
boundaries: for every condition, lookup, arithmetic, conversion and mutation on the statement, one line per boundary the type permits: zero, negative, empty, absent key or nil, false, the maximum, a repeated or concurrent call, a receiver that is shared or immutable (a literal, a constant, class-level state): <value> -> <what happens>; intended per <file:line> | NOT SHOWN
breaks when: <the input, state or sequence that would make the statement wrong; for a modified or removed statement, also what the old code did that this no longer does, including checks, cleanup, ordering, logged fields and error handling>; ruled out by <file:line, quoted> | NOTHING IN THE REPOSITORY RULES IT OUT
verdict: DEFECT, <trigger> | LATENT, <the assumption outside the repository, or the boundary whose intent is NOT SHOWN> | SOUND
Lead: <tool, rule>: accepted, see verdict | refuted by <file:line, quoted>     (only when the line carries a lead)
```

`names` opens every definition and cites it, starting from the pack's definitions and occurrence lists; a `names` with no file and line is unfinished, and a token that is not defined anywhere (a tag, a key, a message) is compared with every other place the same token, or a near spelling of it, occurs in the diff, the file and the pack's occurrence list. A `names` that answers NO for any token is itself a finding: the row's verdict is DEFECT when the disagreement changes behavior and LATENT otherwise, never SOUND, and the item states both spellings or definitions and where each is used. `boundaries` is written out even when every boundary is handled: a boundary where the behavior differs from the ordinary case, with an observable consequence (a wrong result, a skipped write, an exception, a lost record), and no cited line shows the difference is intended makes the row LATENT; a boundary that merely produces a different but equally valid result is SOUND. `breaks when` names a concrete input, state or sequence and then either the cited line that rules it out or the statement that nothing does; a candidate from the hunk's list that no row rules out is carried into the row of the statement it concerns. The verdict follows: DEFECT when the breaking input is reachable; LATENT when the statement is correct only under an assumption the repository does not establish (who can set a setting, how a binary is invoked, what a response always contains, which interpreter or runtime options are in effect, which caller supplies the value) or when a boundary is NOT SHOWN; SOUND only with the citations.

The auditor returns the ledger file's path, its row count, the counts of DEFECT and LATENT rows, and any lines it did not reach, by file and line range, at the top of its result; it never leaves a line out silently.

**Coverage check.** Before merging, write a script that lists every (file, line) the dealt hunks contain, changed and context, and checks that each falls inside a row's key range in the ledger of the auditor it was dealt to. Give every missing line to a fresh auditor with the ledger duty alone and repeat the check, until no line is missing or three rounds have passed; lines still missing after that are named in the review summary as not audited. Then read every DEFECT and LATENT row and every row whose `names` answers NO, from every ledger (the verdict tokens and the NO answers are easy to extract); never a subset of the ledgers.

**File owners.** Independently of the audit, give each changed source file to an owner who reads the pack and then the whole file at the head, top to bottom, not only the hunks, and checks that the changed code agrees with the rest of the file and its class or module: the same names, keys, tags and spellings as sibling code that does the same job; calls dispatched through the same receiver or helper the sibling methods use for the same purpose; shared state read and written under the same lock or initialization discipline as elsewhere in the file; the same error handling, logging fields and return conventions; and every place in the file that the changed code should have changed too. A file owner reports each disagreement as an atomic item with the sibling line cited. When there are more than twelve changed source files, group them so that no owner has more than about 2,000 lines to read and no more than twelve owners run; files that are only moved or renamed without content change need no owner. A file longer than 2,000 lines is read as its top-level structure (imports, constants, class and function signatures) plus every function or class that contains a change, not line by line.

**Reviewers.** Independently of the audit and the owners, run six reviewers that each receive the pack, the diff, the brief and read access to the repository, and never see each other's output, the ledgers or the owners' notes. Use the agent's subagent mechanism when it has one; otherwise run the six sequentially, each from a fresh start with only the pack and the brief, and keep their results in separate files so no pass reads another's notes.

- **Coverage**: walk every changed hunk and check null, undefined and empty-collection paths, including every lookup whose result can be absent and every function path with no return value; inverted or incomplete conditions and boundary errors; wrong comparison operators or reference equality where value equality was meant; promises created but not awaited, including inside forEach or map callbacks; hardcoded literals where a variable or field was meant; case, normalization and regex-anchoring mistakes when matching strings, such as a suffix match where a whole-domain match was meant; a query or filter whose new condition applies more widely than the sibling conditions around it; error handling that changes the response status or swallows failures; resources never released; branches the change makes unreachable; loops whose exit condition reads a value that does not change.
- **Literals and definitions**: for every identifier, key, parameter name, HTTP verb, property, enum value, vendor-prefixed CSS property and numeric constant the diff introduces, open the thing it refers to (the route table, the schema, the type, the framework or browser documentation, the value before the change) and confirm it exists and means what the code assumes. Check that each changed file's contents match its name and purpose, that a test calls the route with the verb the router declares, and that every edit mirrored from one place to another preserves the original values.
- **Contracts**: for every changed signature, return shape, schema, query or type, trace every caller and implementation across the repository and report each place that now disagrees with the change, including implementations of a changed interface that still declare the old shape. When a synchronous function became asynchronous, list every caller that still uses its result synchronously.
- **State and failure paths**: read-modify-write sequences that are not atomic under concurrent requests, lazily initialized shared state read from several threads, stale reads, missing transactions, partial updates, retry and idempotency gaps, cancellation and resource lifecycle; migrations whose new columns leave existing rows null or without the default the code assumes; sibling code paths that handle the same event asymmetrically, where one path persists or cleans up and the other does not; then construct concrete edge inputs and operational sequences for the changed behavior and trace each through the code until it produces a wrong result.
- **Security**: for every changed path, ask who controls each input and what it reaches. Network requests to a URL that comes from configuration, a setting or a request (server-side request forgery); origin, host and referer checks done with substring or prefix matching instead of exact comparison of scheme, host and port; security headers added, removed or weakened, such as frame options, content security policy or CORS; values interpolated into HTML, JavaScript, SQL, shell commands or templates without escaping or binding; state-changing GET routes and other requests without CSRF protection; authorization checks that are skipped on one branch, bypassed by a cache or a fallback value, or that trust a cached grant while ignoring a cached denial; secrets, tokens or private fields exposed by a new serializer field, log line or response.
- **Refactor fidelity**: for every block the diff replaces, moves, extracts or rewrites, list what the old code did, including nil and empty checks, logged fields and identifiers, error handling and the errors returned, blocking versus asynchronous behavior, ordering and retries, and confirm each behavior survives in the new code; a refactor that drops one of them is a defect even when the new code reads cleaner. Also check that error messages and returned error types describe the condition that actually occurred, that newly required behavior has a test and that the test exercises the new arguments, and that changed comments, docs and messages are still true.

Each reviewer and each file owner returns atomic items, one defect per item: file and line of the statement that is wrong, root cause, trigger (the input, state or sequence), observable bad outcome, evidence from the repository, suggested fix, severity (critical, high, medium, low). A reviewer reports every defect it has a concrete trigger for and nothing it does not. Describe an attacker-controlled input by its property (a URL containing a quote character, a hostname that is a prefix of the allowed one, an address inside the private range), never as a working payload, script or exploit string; a finding states the mechanism and the class of input that reaches it, which is what a maintainer needs to fix it.

## 3. Merge

Cluster the reviewers' items, the file owners' items, the accepted leads and the ledgers' DEFECT and LATENT rows by underlying defect, not by wording or line. Keep the strongest trigger and evidence for each cluster, and record how many of the six reviewers, whether the auditor of that line, and whether the file owner or an analyzer reported it. One item per defect. Merging removes duplicates only; it never removes a finding. A LATENT row or an unrefuted lead that nobody else reported stays a finding at nit severity.

## 4. Verify, cheaply and optionally

Proof strengthens a finding; it never gates one. Where a cheap check exists, run it, cheapest first: the language's compiler or type checker on the changed package; a throwaway script under /tmp that calls the changed function with the item's trigger, with external services mocked; a focused test in the project's framework only if its dependencies install quickly. Installing a missing toolchain with sudo apt-get or running one from a Docker image is fine. Do not install the whole repository, do not run the full test suite (the change already passed CI with its defects in), do not let setup consume the review, and do not modify the checkout. Never write a script that exercises an authentication or authorization bypass, forges a credential or token, or constructs attacker input; a security finding is verified by reading the code path, and its trigger is described, not executed.

## 5. Publish

Post every merged item unless a cited line makes its trigger impossible. Do not drop a finding because it depends on a particular input or state, or because no caller reaches it today; that is what a trigger is, and a latent defect is published as a nit with its trigger. Nothing is posted to say that a line is safe: a SOUND row stays in the ledger.

Anchor each finding on the statement that is wrong. When the wrong statement is in a callee or a helper, anchor there and name the caller in the text; when the same defect appears at several statements, anchor on the first and name the others. Write each finding as mechanism, then consequence, in one or two sentences, followed by the trigger and the fix. A LATENT item says what assumption or boundary makes the statement correct only sometimes, what happens otherwise, and that the repository does not show it. A finding that came from an analyzer names the tool and rule. Say when a check reproduced it, and end every finding with who found it, in the form `(found by 2 of 6 reviewers, auditor, file owner)`, listing only the sources that reported it; a line audited in a catch-up round counts its catch-up auditor as the auditor. Severity: p1 only when you would block the merge yourself; other critical, high and medium findings are p2; low, latent and analyzer-only findings are nit. Post once, as a single review with the inline findings ordered p1, then p2, then nits, and within the nits first the low-severity defects, then the `names` disagreements and unrefuted analyzer leads, then the latent items; then a short summary that also names any lines that were never audited. At most 30 inline comments: anything beyond the 30th is listed in the summary instead, one line each with its file and line, because tooling that reads a review sees only its first 30 inline comments. When nothing survives, say so in one sentence rather than inventing findings.
