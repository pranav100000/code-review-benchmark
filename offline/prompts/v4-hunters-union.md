Review this pull request for defects using independent parallel hunters, then publish the union.

Setup. Determine the merge base, head commit, changed files and changed line ranges. Write a short context pack: what behavior each hunk changes, which public contracts and callers are involved, and which tests and schemas touch the changed code. Every hunter gets the diff, the context pack and read access to the repository. Hunters never see each other's findings.

Hunters. Spawn these four as independent subagents and wait for all of them:
1. Local semantics: walk every changed hunk and check null, undefined and empty-collection paths; inverted or incomplete conditions and boundary errors; wrong comparison operators or reference equality where value equality was meant; promises created but not awaited, including inside forEach or map callbacks; hardcoded literals where a variable or field was meant; case or normalization mismatches in string matching; error handling that changes the response status or swallows failures; resources never released; branches the change makes unreachable.
2. Contracts: for every changed signature, return shape, schema, query or type, trace all callers and implementations across the repository and report each place that now disagrees with the change.
3. State and concurrency: read-modify-write sequences that are not atomic under concurrent requests, stale reads, missing transactions, partial updates, retry and idempotency gaps, cancellation and resource lifecycle, migrations and cache invalidation, plus authorization and tenant-boundary checks on changed paths.
4. Failure paths: construct concrete edge inputs and operational sequences for the changed behavior and trace each through the code until it produces a wrong result or a contradiction; also check that newly required behavior has a test and that changed comments, docs and error messages are still true.

Each hunter reports every defect it has a concrete trigger for as one atomic item: file and changed line, root cause, trigger, observable bad outcome, evidence from the repository, suggested fix, severity (critical, high, medium, low). No style, naming or refactoring preferences. No speculation without a trigger. Low-severity real defects such as dead code, misleading messages and missing cleanup are in scope.

Publish. Merge the hunters' items by underlying defect, keeping the strongest trigger and evidence for each. Post every merged item once, anchored to its line, stating the mechanism and then the consequence in one or two sentences, with the trigger and the fix. Severity mapping: critical and high findings are p1 only when you would block the merge yourself, otherwise p2; medium is p2; low is nit. Do not drop a finding because it depends on a particular input or state; drop it only if the repository shows the trigger is unreachable. Do not report anything about the environment you reviewed in.
